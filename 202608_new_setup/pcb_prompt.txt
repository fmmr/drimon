## Context you also need to know (added since last brainstorm)

- **Panic-loop crisis, 2026-08-07 through 2026-08-13.** For a full week the deployed board (v1.2, firmware 60abeb8) went into nightly panic-reboot loops (25 k+ wakes overnight, ~1.6 s per cycle), draining the battery ~5-8 mAh net each night. Investigation ended with a diagnosis of **failing pack + high internal resistance under load**, not the firmware and not the solder joints (which were checked and confirmed OK). The DFR0559 charger, when unloaded, clamps the shared BAT node to its CV target and *hides* the true cell EMF from the fuel gauge — so we spent days chasing wrong theories about firmware, WiFi retries, and solder joints when the actual issue was the pack. Full incident timeline preserved in `documentation/HARDWARE_SOLAR_CHARGING_CHECK.md`-style detail is scattered across the raw statuses at drimon.rodland.no; the design-relevant lessons are all captured in the doc's **Power debuggability** section and the new **CHG_DISC** MOSFET (see below).

- **Firmware fixes deployed 2026-08-13 (commit 0cd7dc1 and follow-ups)** and validated across the first clean night 2026-08-13/14:
  - Fresh `WiFiClient` per POST attempt (avoids lwIP PCB reuse under retry stress)
  - `MAX_POST_RETRY 2 → 1` (halves retry blast radius)
  - `P1`/`P2`/`P3`/`PA` stage breadcrumbs inside `postThingSpeak` for pinpointing crash location
  - **Circuit breaker (CB)**: any bad reset (PANIC / WDT / BROWNOUT / SW / unknown) triggers a stage("CB") + NIGHT-interval deep sleep. Turns a panic loop into a 20-min back-off. Fired exactly once during the first clean night — caught a single brownout, resumed normal operation. Confirmed working as designed.
  - Unified `enterDeepSleep(long start, const char* finalStage, float lux)` — single exit point from setup(), used by both normal end-of-wake and CB early-exit.
  - Do NOT touch firmware this session; note it here only so you know what state the deployed system is in.

- **New PCB design has grown two new features** as a result of the debugging week — both already documented in NEW_PCB_DESIGN.md:
  - **Power debuggability** (test points, per-rail status LEDs, inline 0Ω isolation resistors, debug header + optional breakout pigtail, firmware-side rail-voltage telemetry tokens `V5-`, `V3-`, `BV-`, `BVR-`)
  - **CHG_DISC P-MOSFET** between battery+ and DFR0559 BAT+ pin — firmware can pulse it open briefly to get a bias-free battery voltage reading (`BVR-` token) that isn't clamped by the CV charger. Safe because ESP32 no longer depends on the DFR0559's boost — it runs from the LDO path.

- **Enclosure requirements captured** (see A1 in the open questions):
  1. Easy mounting for every part
  2. As small as practical
  3. Simple install/uninstall for pressure washing + winter storage; as few external cables as possible, each easy to unplug
  4. LEDs + both displays + buttons front-visible
  5. Mounted underside of an existing shelf (front-facing direction = downward-visible)

- **LoRa / Meshtastic as new uplink direction.** Greenhouse WiFi is unreliable — not just locally, but the internet uplink is a 10 km directional-antenna WiFi link that fails hard and often. Design intent for the new PCB is to switch primary uplink to **LoRa via SX1262 using Meshtastic protocol**, riding the public mesh (Rødtangen has visible coverage on <https://analyzer.letsmesh.net/map>). Keep WiFi as a fallback during validation. Three architecture options captured as open question A8 — hardware topology depends on coverage test result from a first-buy Heltec V3.

## Framing — do not slip on this

The current v1.2 PCB, its wiring topology, and its enclosure arrangement are **not constraints** on the new design. Only the sensor set (what data firmware collects) is carried forward. Everything else — physical layout, PCB pin assignments, connector choices, sensor mounting, enclosure geometry, whether the DFR0559 / MAX17043 sit integrated on the main PCB or remain as separate modules — is fully open. The v1.2 lessons appendix in the doc explains what to protect against; it is context, not a template.

Similarly: KiCad, Aisler, 2-layer FR4 are all **working assumptions**, not requirements. If a better tool, fab, or layer count fits the design when we get there, we take it.

## Style

- Call BOSS "BOSS".
- BOSS is a strong Kotlin/Java/C++ dev, not an EE. Can solder, doesn't natively read schematics or reason about analog circuits from first principles. Explain hardware trade-offs from first principles; don't just name parts. When BOSS asks "why", assume they mean it — no jargon-shortcuts.
- Don't quote the design doc back to BOSS as if it were external evidence. BOSS is the author; the doc is our shared notes, not an authority.
- For critical or unattended workflows, prefer hardware (a $2 IC) over firmware workarounds when both are viable. The flashing decision in the doc is an example.
- Don't narrate; act. Terse updates at key moments. Give a one-line commit message when a task is done.
- The I²C socket pinout is locked to `SDA – SCL – VCC – GND` so existing sensor plugs carry over — do not renegotiate.
- Don't touch firmware in this session. It's a hardware-design session only. (Firmware is currently healthy on 0cd7dc1+.)
